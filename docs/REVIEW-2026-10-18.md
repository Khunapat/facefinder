## Blocker

### B1. Any judge can delete or rescan the shared sample album for everyone

- **Where:** `app/main.py:219` (`delete_album_data`) and `app/main.py:468`
  (`start_index` with `rebuild`). Neither checks for the sample album. The menu
  items show for every ready album (`app/static/index.html:958`), the sample
  included.
- **What goes wrong:** the sample album's scan is one shared copy (that is the
  design: `_need_album` lets anyone who can open the folder use it). "Delete
  this album's data" calls `store.clear_album()` and `store.forget_ai()`, which
  wipes the face data **and** the Gemini cache for every judge. "Rescan from the
  start" calls `clear_album()` as well and scans the whole album again. (The
  API also accepts `rebuild` with `file_ids`, which would shrink the scope to the
  picked photos; the page's only caller, `index.html:1007`, does not send
  `file_ids`.)
- **How to trigger:** judge A signs in, opens the Sample album card, opens the
  album menu and chooses "Delete this album's data" (a natural thing to try
  after reading the privacy window, which the deck and SUBMISSION point to).
  Judge B now opens the sample and gets the photo chooser with nothing scanned.
  The scan runs again, and because the Gemini cache was deleted too, every photo
  goes back to Gemini. With Rescan, every judge who has the sample open at that
  moment sees their screen switch to the scan card, because `pollStatus`
  (`index.html` around line 1294) sees `status != "ready"` and locks the work
  area.
- **Smallest fix:**
  1. Server: in `delete_album_data`, and in `start_index` when
     `body.get("rebuild")` is set, add:
     ```python
     if config.SAMPLE_ALBUM and folder_id == gd.parse_folder_id(config.SAMPLE_ALBUM):
         raise HTTPException(403, "The sample album is shared by everyone, so it cannot be deleted or rescanned.")
     ```
  2. Page: send `sample_folder_id` from `/api/me` (`app/main.py:184`) and hide
     `#menuDelete` and `#menuRescan` when `state.folderId` equals it.
  Step 1 alone is enough for safety: the existing `notice()` shows the message.

## Should fix

### S1. Deleting a big album may outlast Firebase Hosting's 60 s limit

- **Where:** `app/main.py:219-238`, `app/store_firestore.py:135-141`.
- **What goes wrong:** the delete runs inside `with _jobs_lock:`. On Firestore,
  `forget_ai` runs **one query per photo** (`where file_id == f`) and deletes
  each hit, one after another. Firebase Hosting cuts a request to Cloud Run at
  60 s, so on a big album the browser can get an error page while the server
  carries on. Meanwhile `_jobs_lock` is held, so on that instance, scan
  start/stop, the end of any other scan, and status checks for an album that is
  scanning (`_settled`) all wait.
- **How to trigger:** open an 800+ photo album that has been scanned, then
  "Delete this album's data". **I could not confirm the timing:** 800
  sequential Firestore queries plus deletes is roughly 20 to 60 s, depending on
  latency.
- **Smallest fix:** keep `clear_album` in the request, but move
  `store.forget_ai(ids)` out of the lock and into a daemon thread
  (`threading.Thread(target=store.forget_ai, args=(ids,), daemon=True).start()`).
  Alternatively, batch the Firestore query with an `in` filter of up to 30 ids
  per query.

### S2. README tells owners to keep the OAuth app in Testing mode

- **Where:** `README.md:158-160` ("leave the app in **Testing** mode and add your
  friends' emails as test users").
- **What goes wrong:** in Testing mode, a judge who is not a listed test user
  is blocked at Google sign-in. They would not see the "unverified app" warning
  that the README's own For judges section describes. HANDOFF section 11 says
  the app is published (In production), but HANDOFF section 5 still lists
  publishing as open. **I could not confirm** which is true: check Google Auth
  Platform, then Audience, then "Publishing status: In production".
- **Smallest fix:** rewrite the paragraph: "FaceFinder is published (In
  production) without verification, so anyone can sign in after Google's
  'unverified app' warning."

### S3. README's Cloud Run deploy command is stale and would break scans

- **Where:** `README.md:275-288` (Option C).
- **What goes wrong:** the command has `--memory 2Gi`, no `--max-instances 1`,
  no `--no-cpu-throttling` and no `STORE=firestore`. HANDOFF section 4 explains
  that scans and exports run in background threads with in-memory state, so
  more than one instance, or a throttled CPU, breaks them, and without Firestore
  the index is lost on every restart. The text also says "it scales to zero so
  an idle app costs nothing", which no longer describes the setup.
- **How to trigger:** anyone (a judge reading the repo, or a teammate)
  deploys with that command, then starts a scan; progress stalls or vanishes.
- **Smallest fix:** replace the block with
  `CPU=4 bash scripts/deploy-cloudrun.sh` and one line on what it sets.

## Nice to have

### N1. Gemini's queue holds full-size thumbnails

- **Where:** `app/main.py:396` and `app/main.py:405` submit `data` (the 1600 px
  scan thumbnail); `gemini.shrink()` runs later inside `judge`.
- **What goes wrong:** when the face scan runs ahead of Gemini (24 Gemini
  workers versus a faster local scan), every waiting photo keeps its full
  thumbnail in memory until Gemini takes it. At an estimated 200 to 400 KB each,
  a backlog of a few hundred photos is around 100 MB, which is fine at 8 GiB.
  Several thousand photos could reach 1 GB or more. **I could not confirm** the
  real backlog size on Cloud Run.
- **Smallest fix:** shrink before submitting:
  `gem.submit(judge, meta, gemini.shrink(data))`, and drop the `shrink` call
  inside `judge`.

### N2. "Suggest folders" can run past Firebase Hosting's 60 s limit

- **Where:** `app/main.py:858-868` calls `gemini.suggest_groups()` while the
  request waits; `_call` in `app/gemini.py` makes up to 5 attempts of up to
  60 s each, with sleeps of 2, 4, 8 and 16 s.
- **What goes wrong:** if Gemini is slow or rate-limited, the request outlives
  Firebase Hosting's 60 s cut and the page shows a generic error.
- **How to trigger:** only when Gemini returns 429 or 5xx, or hangs. **I could
  not confirm** how often that happens.
- **Smallest fix:** give `_call` an `attempts` argument and pass `attempts=2`
  from `suggest_groups`.

### N3. Saved names can be dropped from the server after changing Grouping

- **Where:** `app/static/index.html:1828-1846` (`applyServerNames`) and `1813`
  (`saveNames`).
- **What goes wrong:** `applyServerNames` places a saved name only if a group
  shares at least 30% of its photos. A name that is not placed is not in
  `state.crowd`, so the next `saveNames()` POSTs a list without it and the
  server loses that name for good.
- **How to trigger:** name 5 people at Grouping "Balanced", switch Grouping to
  "Strict" (groups split), tick any card, sign out and sign in on another
  browser: some names are gone. In the same browser tab, sessionStorage hides
  this.
- **Smallest fix:** keep the unplaced entries (`state.namesUnplaced`) in
  `applyServerNames`, and append them to `people` in `saveNames`.

### N4. Progress checks report a 403 as "Lost the connection"

- **Where:** `app/static/index.html:935-943` rethrows only a 404.
- **What goes wrong:** a 403 from `_need_album` (access removed during an
  export or sort) is retried 5 times, about 22 s, then shown as "Lost the
  connection. The work carries on".
- **Smallest fix:** `if(e.status && e.status < 500) throw e;`

### N5. An expired sign-in looks like "no access to this folder"

- **Where:** `app/main.py:95` maps 401, 403 and 404 alike to the `no_access`
  box ("You no longer have access to this album").
- **What goes wrong:** if the Google sign-in can no longer refresh (revoked, or
  a 7-day Testing-mode expiry), the page explains folder sharing instead of
  "sign in again".
- **Smallest fix:** handle 401 separately:
  `raise HTTPException(401, "Your Google sign-in has run out. Sign in again.")`.

### N6. Rescan reuses Gemini's old notes even when the photo changed

- **Where:** `app/main.py:327-334`.
- **What goes wrong:** `saved_ai` is keyed by file id only, and it is stored
  under the photo's **new** checksum, so a photo that was edited in place in
  Drive keeps its old description and score.
- **How to trigger:** rare. Replace a photo's content in Drive while keeping
  the same file, then "Rescan from the start".
- **Smallest fix:** since `judge` now always calls `cache_ai` with the right
  checksum, `saved_ai` only matters for photos judged before this change. Keep
  it, but skip a photo whose `cached_ai(ai_key)` already exists, or accept the
  rare case.

### N7. SQLite `forget_ai` treats `_` as a wildcard

- **Where:** `app/store.py:205-209`: `LIKE 'id:%'`, and Drive ids often contain
  `_`.
- **What goes wrong:** deleting one album can delete another photo's cached
  Gemini note. This affects local SQLite only; Cloud Run uses Firestore.
- **Smallest fix:** `DELETE FROM ai_cache WHERE substr(key, 1, ?) = ?` with
  `len(f) + 1` and `f + ":"`.

## Checked and fine

- **`_need_album` on album routes:** every route that takes a `folder_id` calls
  it, including the new `delete`, `names` GET/POST and `status`. Routes without
  it: `/api/thumb/{file_id}` uses the caller's own Drive token, so Drive itself
  refuses photos the caller cannot see. `/api/albums/recent` and
  `/api/albums/forget` touch only the caller's own list. `/api/album` checks
  Drive directly.
- **PKCE and OAuth state:** `login` stores `oauth_state` and the
  `code_verifier`. `callback` rebuilds the flow with that state and verifier,
  and `fetch_token(authorization_response=...)` checks the state. The new early
  return (`?signin=retry`) only skips cases that would have failed anyway.
- **Export:** `app/main.py` `export` refuses any file id not in
  `_ready_photos(folder_id)` ("Export contains photos outside this album").
- **XSS:** every `innerHTML` place I traced that shows album names, person
  names, file names, Gemini reasons or descriptions, sort folder names or notes,
  or error messages goes through `esc()`. Places checked: recent cards, the
  chooser, the result cards (`groupCard` title and note), the preview "why"
  line, the Cull summary, the export list, the no-access box (the email and the
  link, with `link` limited to `http(s)`), `notice()` and the delete message.
  `esc()` escapes `& < > " '`.
- **Between two users:** `_face_cache` and `_thumb_meta` are now keyed by
  access token. Names are keyed by a hash of the email plus the folder. Sort and
  export jobs check `_job_owner`. The delete route removes only the caller's
  names and recent entry; the shared scan removal is documented in the privacy
  window.
- **Secrets:** none found. HEAD has only the placeholder
  `GOCSPX-xxxxxxxx` in `.env.example`. Searching all history for Google client
  secrets, API keys, private keys and access tokens found nothing, and no
  `.env`, service-account or token file was ever added.
- **Session cookie:** named `__session`, which Firebase Hosting requires.
- **Sign-in from `.run.app`:** `refreshMe` moves the page to `PUBLIC_BASE_URL`
  before anything else. A sign-in that was started on `.run.app` anyway comes
  back to `/?signin=retry` with a clear message.
- **Stop and Resume:** Stop no longer waits for Gemini. A scan that died with a
  restart is marked "stopped" after 90 s without a heartbeat (`_settled`), and
  Stop on a dead scan marks it stopped too. Resume skips photos already scanned.
- **After a restart:** sort and export status return a 404 with a clear
  message, and the page's `retrying()` passes the 404 through. A repeated export
  skips photos already copied (`ff_src`).
- **Gemini 60 s limit:** `_HTTP = {"timeout": 60_000}` is set on both client
  types and is in milliseconds, as google-genai expects.
- **Exports saved inside the album** are skipped by later scans
  (`list_images`, `appProperties`).

### N1: one unreadable image now stops the whole scan (should fix)

- **Where:** `app/main.py:406` (`one`) and `app/main.py:415` (`rejudge`) now
  call `gemini.shrink(data)` before submitting, outside any `try`.
  `gemini.shrink` raises `ValueError("unreadable image")` when OpenCV cannot
  decode the bytes (`app/gemini.py:176-180`). Before this commit the same call
  ran inside `judge`'s `try/except`, which swallowed the error.
- **What goes wrong:** `faces.analyze` does not raise on undecodable bytes; it
  returns `([], None)` (`app/faces.py:140-142`). The photo is saved, and then
  `shrink` raises. `list(pool.map(one, todo))` re-raises it, and the scan ends
  with status `error` and the message "unreadable image"
  (`app/main.py:445-446`). Retry fails the same way in `rejudge`, so the album
  never reaches "ready" and the work area stays locked.
- **How to trigger:** Gemini is on (as on Cloud Run) and the album holds one
  `image/*` file that OpenCV cannot decode and that has no usable Drive
  thumbnail (for example some HEIC or RAW files). Before this commit the same
  album finished "ready" with "Gemini could not check 1".
- **Smallest fix:** in `one`, wrap the shrink in its own try and return on an
  error:
  ```python
  if gem and not from_cache(meta):
      try:
          small = gemini.shrink(data)
      except Exception:
          return
      sent.append(gem.submit(judge, meta, small))
  ```
  In `rejudge`, move `gemini.shrink(data)` inside the existing `try`.

### N5: an expired sign-in still gives a 500 in the common case (not fixed)
